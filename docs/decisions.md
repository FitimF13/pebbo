# Decisions

All decisions were made on 2026-11-19 during the initial brainstorming. A decision changes only by adding a new entry that replaces an old one.

| # | Topic | Decision | Why | Rejected alternatives |
| --- | --- | --- | --- | --- |
| 1 | First focus | Natural spoken conversation comes first | Everything else builds on talking to Pebbo | Starting with memory, smart home or hardware |
| 2 | Hardware timing | No hardware is bought until everything runs on the gaming PC | Faster iteration, and the case must fit parts chosen after the software works | Building the device in parallel |
| 3 | Always-on core | A mini PC at home, budget about 150 (Intel N100 class) | Reminders, routines and the app need something that never sleeps, and data stays in the house | VPS as core (data leaves the house), gaming PC only (Pebbo disappears when it is off), 600 to 1500 mini PCs (too expensive) |
| 4 | Main language model | Local. Stronger compute is added as optional workers or providers | Privacy and no running costs | A paid API by default |
| 5 | Compute management | Owners pair and remove compute devices and providers in each Pebbo's settings, with routing rules | Flexible across cheap boxes, gaming PCs and future hardware | Fixed configuration files |
| 6 | Subscriptions | Claude and Codex adapters only if their terms allow it, optional, off by default, each person's own sign-in | Anthropic's terms forbid subscription tokens in third-party tools since February 2026. OpenAI documents a custom-client path that still needs checking. | Shared logins, routing other people through one subscription |
| 7 | Voice pipeline | A cascaded pipeline with streaming, turn detection and backchannel handling, behind interfaces | Works today on local hardware in German | Waiting for full-duplex speech models, which are English-first and too large today |
| 8 | Language | Standard German first, Swiss German later (replaced by #90) | Local recognition is reliable for standard German | Swiss German from the start |
| 9 | Smart home | Home Assistant, fully local, cloud integrations and analytics off | Open source, local, controls Hue directly, huge device support | openHAB, ioBroker, Hue Bridge only, any vendor cloud |
| 10 | Music | Music Assistant for Spotify and YouTube Music. Targets: Bluetooth box, Pebbo's speaker, network speakers | Covers both accounts and all target types | Building provider integrations ourselves |
| 11 | Reaching people | Own phone app with push (app type replaced by #29) | Free, private, no dependency on a messenger | Telegram, WhatsApp or Signal as the main channel |
| 12 | VPS role | Relay for remote access and push, with no household data in plain text | Remote access without opening the home router, while data stays at home | VPS as core or data store |
| 13 | Licence | Apache-2.0 for code, CERN-OHL-P v2 for hardware, CC BY 4.0 for documentation | Fully open source, community friendly, patent grant | Non-commercial licences (not open source, put off contributors), AGPL |
| 14 | Personality | Cheeky and warm | Feels like a friend, matches the concept | Calm and reserved, per-person tone as the default |
| 15 | Proactive behaviour | Reminders, morning briefing, and small talk and tips, with strict rules and limits | Makes Pebbo feel alive without becoming annoying | Speaking only when addressed |
| 16 | Memory | Facts and preferences, conversation summaries, plans and lists, all visible and deletable | Useful everyday memory with full control | Remembering only on explicit command |
| 17 | Reminder delivery | Speak when the person is near, otherwise push, based on local presence signals | Right channel without announcing private things to others | Always speak, always push, GPS tracking |
| 18 | Calendars | Own local calendar plus opt-in connectors for iCloud, Google and Microsoft 365, read-only first | All four are in use today | One calendar only |
| 19 | Routines | Every person can teach routines in plain language. Pebbo confirms, saves and runs them, with safety rules | Pebbo grows with its people | Routines only through a technical editor |
| 20 | Voice onboarding | Gradual learning in daily use, owner adds people, confirmation in the app, guest mode for unknown voices | Low effort for people, safe against impersonation | A formal enrolment session, ignoring unknown voices |
| 21 | Face and lights | Concept-image style with basic states, feelings, idle life and touch. LED ring and wings show status, mood and notifications | Cute, readable, light enough for small hardware | Detailed or pixel-art faces |
| 22 | Office instance | Same features as home plus end-of-day handoff, work calendar and tasks, approved PC tasks | One product for both places with strict separation | A separate office product |
| 23 | Rejected base projects | Do not build on the Xiaozhi server or OpenClaw | Xiaozhi's server contacts external services by default. OpenClaw had a serious security issue and a broad attack surface. | Adopting either as the core |
| 24 | Dialogue agent | Pydantic AI with tools exposed through MCP | Proven, typed, supports many providers and custom model adapters (for example a Codex app server adapter) | A custom loop (more code), Pi with Pi Durable (experimental, TypeScript) |
| 25 | Remote access | Headscale on the VPS with the Tailscale client on phones | Private network without open ports at home, self-hosted | An outbound tunnel with a public domain |
| 26 | Technology stack | Python with FastAPI and Pipecat for the core, TypeScript with React and Vite for the apps, SQLite with sqlite-vec, Docker Compose | Best ecosystem for audio and speech, one web code base for phone and PC | Node.js for the core, separate native apps |
| 27 | Reused components | Home Assistant, Music Assistant, Radicale, Headscale, Pipecat, openWakeWord, faster-whisper, SpeechBrain, Ollama | Reuse before build. See the component map in the [architecture](architecture.md#component-map). | Building these ourselves |
| 28 | Subscription adapters | Reach Claude and Codex subscriptions only through their official clients (Claude Code CLI, Codex app server) signed in by the person, as T3 Code does. Only for hard questions, not realtime conversation. | Pebbo never touches subscription tokens. The realtime conversation needs the low latency of the local model. | Extracting OAuth tokens, calling subscription endpoints directly, the Claude Agent SDK with a subscription |
| 29 | Phone apps | Native iOS and Android apps with React Native and Expo, builds through Codemagic | Apps must feel as native as possible. An Apple developer account is available. React Native shares TypeScript and logic with the web app. | An installable web app (not native enough), Flutter (second language) |
| 30 | App design | Pebbo's character combined with the modern feel of current apps such as ChatGPT and the T3 Code mobile app | Cute and recognisable, but clean and modern | A plain system look, a purely playful look |
| 31 | App distribution | Everyone can build and install the iOS and Android apps themselves from the repository. The project additionally publishes the iOS app in the App Store as a convenience, because it needs the app itself. | Self-hosting stays fully possible, iPhone users can simply download | App Store only, or self-build only |
| 32 | Push for the published iOS app | A small, open-source push gateway run by the project forwards end-to-end encrypted notifications to Apple. Android uses UnifiedPush or Firebase Cloud Messaging. | Apple requires the publisher's key. The gateway sees only device tokens and ciphertext. | Each self-hoster needing their own Apple account, unencrypted notifications |
| 33 | Language model | Ministral 3 8B through Ollama, as a derived model `pebbo-ministral` with a 4096-token context, kept loaded | The most natural and characterful German of the tested local models (Qwen 3 4B and 8B, Gemma 3 4B), first token in about 0.1 s, fits next to Whisper in 8 GB, Apache-2.0 | Qwen 3 (weaker German), Gemma 3 (custom licence, ignored the tag format) |
| 34 | Speech synthesis | Pocket TTS with its German model on the CPU (voice see decision 40) | Streams the first audio in about 0.2 s on two CPU cores, so it will also run on the always-on box. MIT code, CC BY weights. | Chatterbox (pins old libraries and pulls in Gradio), Piper (GPL and mostly non-commercial German voices), Voxtral TTS (non-commercial weights) |
| 35 | PC app connection | Own small WebRTC client in the browser, talking Pipecat's RTVI messages over a data channel, without ICE servers | Pipecat's browser transport depends on Daily's SDK, which may load code from Daily's servers. Without ICE servers no public STUN server is contacted. | Pipecat's JavaScript transport, WebSocket audio |
| 36 | Wake phrase | Phonetic matching of "Pebbo" in Whisper transcripts, with a greeting or followed by more words | Works now without training data. A lone name is ignored, because Whisper sometimes hears it in "mhm". | A trained acoustic wake word (openWakeWord), planned for the always-on box |
| 37 | Runtime network guard | The core blocks every TCP connection and UDP datagram to a public address, and switches off the telemetry of ONNX Runtime and Hugging Face | A test showed that ONNX Runtime sends telemetry and aiortc uses a public STUN server by default | Relying on configuration alone |
| 38 | Remote access (revisits #25) | Prefer Pebbo's own device pairing with per-device keys plus an end-to-end encrypted relay on the VPS, so phones need no extra app. Headscale stays the fallback. Final choice in phase 4. | Every device is registered once and can be revoked, and no VPN app is needed on phones | Requiring a Tailscale or Headscale client on every device |
| 39 | Ending and ignoring | "Stopp", "Halt" or "Ruhe" end the conversation without an answer, a goodbye ends it after Pebbo's goodbye, and the model answers `[ignore]` when people clearly talk to each other | First test: Pebbo kept listening after "stopp" and "bye bye", and it answered everything said in the room | Ending only by timeout, a separate addressee classifier |
| 40 | Tone and voice | Natural and warm with an occasional dry joke, one or two sentences, voice "vera" at normal pitch | First test: answers felt too long and forced in their humour. Vera was preferred in a listening test of ten voices. | Always joking, a pitched-up voice |
| 41 | Whisper decoding | Greedy decoding without carried-over context | About three times faster than the default beam search with the same result on spoken turns | Beam search with five beams |
| 42 | Control centre | The full control centre is a web UI in the browser, served by the core. The iOS and Android apps are a slimmed-down control centre for daily use: chat, reminders, approvals, push and switching between home and office, with links to the web control centre for everything else. | Detailed settings are rare and need space, daily actions need a fast native app. No duplicated settings screens. | A full control centre in every app |
| 43 | Instance storage | One SQLite database per instance in the user's data directory (`%LOCALAPPDATA%\\Pebbo` or `~/.local/share/pebbo`), outside the repository. Tables for people, voice fingerprints, voice claims, memories and reminders. | Simple, local, easy to back up and inspect | A separate database server |
| 44 | Speaker recognition | CAM++ (3D-Speaker, Apache-2.0) through sherpa-onnx on the CPU. A person matches above 0.55 cosine similarity, a fingerprint learns from turns above 0.65, all segments of a turn are identified together, and a short uncertain turn keeps the previous speaker. | Measured on real recordings: the same person scored at least 0.60, different people at most 0.43. Short segments alone were too weak. | SpeechBrain ECAPA (needs torchaudio), per-segment identification |
| 45 | Actions | Requests with action words ("merk dir", "erinnere mich", "vergiss", or "mich ... in einer Minute") go through a separate single-turn tool call. The conversation model then only confirms the result and has no tools itself. | Ministral called tools reliably in short focused requests, but in longer conversations it only chatted about them. Ollama ignores a forced tool choice. | Tools on the conversation model, forced tool choice |
| 46 | Introductions | "Ich bin Sara" from an unknown voice creates a voice claim directly from the transcript. The person or the owner confirms it in the control centre before the voice is linked. | The model did not call an introduce tool reliably. Confirmation stops anyone from claiming to be someone else. | Linking voices without confirmation |
| 47 | Conversation memory | When a conversation ends, the conversation context is cleared and the local model writes a one- or two-sentence summary for the identified person. The last three summaries are part of the next conversation's context. | Pebbo remembers what was discussed, and a guest never sees the previous person's conversation | Keeping the full chat history |
| 48 | Short introductions | Speaker identification keeps one second of audio before the voice activity detector reports speech, and audio too short to identify is kept for the next turn. An introduction heard before the voice is long enough waits for the next sentence. Names are matched to household members by similarity, so a lower-case or misheard name still links. A guest asking to remember or plan something gets a fixed answer instead of a model answer, also when the same request is repeated word for word. | In the first household test a short "ich bin ..." was too short to fingerprint, so no voice request appeared, and the model then claimed to have remembered things for a guest. | A shorter minimum length, which makes fingerprints unreliable |
| 49 | Duplicate facts and reminders | Before storing, Pebbo compares a new fact with the person's facts (text similarity of at least 0.85) and a new reminder with open reminders for a similar task (similarity of at least 0.75) due within ten minutes. A match is reported as already stored instead of being added. | People repeat themselves, especially when unsure whether Pebbo heard them, and duplicate reminders would be spoken twice | Asking the model to check for duplicates, a unique constraint on exact text |
| 50 | Acting (replaces #45 and the transcript part of #46) | Pebbo has no list of command words. Every capability is a tool in a registry with a name, a description, parameters and a permission (everyone, household or owner). After every sentence a focused call to the local model, the action agent, reads the person's last sentence with the two lines before it and what Pebbo knows, and picks tools by their descriptions. The registry checks the permission, the tools run, and only then does Pebbo answer, with the result in its context, so it confirms what really happened in its own words. Facts mentioned in passing are stored quietly as learned. Introductions are a tool too. A spoken-text filter drops sentences that claim an action when none was carried out. Only the wake phrase stays fixed. | New capabilities, such as smart home devices or tools from MCP servers, are added as tools without code for phrases. Answering before acting let the model claim actions that never happened, and a confirmation after the answer was often cut off by the next sentence. In a benchmark of 18 German sentences the agent chose the right tools 17 times, in a median of 0.7 s. | Word lists, tools on the conversation model, acting in the background while answering |
| 51 | Changed facts | A new fact that names the old one it replaces, or that is a close variant of a stored fact starting with the same word (text similarity of at least 0.8), replaces it. | People correct themselves ("jetzt ohne Zucker"), and small models rarely mark that as a change | Keeping both versions, asking the model to delete first |
| 52 | Wake phrase robustness | While Pebbo sleeps, an utterance that does not seem to address it is transcribed a second time without the "Pebbo" hotword. A greeting run together with the name ("Eipepo") or a name split into two short words ("Pei Bo") also counts. | With the hotword, Whisper sometimes dropped a quickly spoken "Hey Pebbo" entirely. Measured on synthetic speech from six voices: 33 of 36 wake phrases recognised, none of 30 other sentences. | A trained acoustic wake word on the PC, which needs a large training set; the device uses its own on-device wake word |
| 53 | Learning at the end of a conversation | Removed. Facts are learned only by the action agent after each sentence. | In a test the end-of-conversation extraction stored vague and wrong facts ("Bestellt regelmässig Tee") and duplicates. Pebbo should rather miss a fact than invent one. | Keeping it with stricter prompts |
| 54 | Body | An Espressif ESP32-S3-BOX-3 on its BRACKET runs the open xiaozhi-esp32 firmware with Pebbo's board code. The core implements the firmware's protocol (OTA answer, pairing, WebSocket with Opus), so a body is a thin client of the same voice pipeline as the PC app. Pairing uses the firmware's activation code, entered in the control centre. | The BOX-3 has echo cancellation on the device with a hardware loopback, so Pebbo can listen while speaking. The firmware is maintained, MIT licensed and contacts only the server it is given. No soldering for the main parts. | Waveshare audio boards (echo cancellation not enabled in the firmware), a DIY ESP32-S3 with I2S parts (no echo cancellation), own firmware from scratch |
| 55 | Network access | The core can listen on the home network for bodies. Body endpoints (`/xiaozhi/`) accept private addresses only, everything else (control centre, PC app) only this computer. | The control centre has no sign-in until phase 4 | Opening the control centre to the network without sign-in |
| 56 | Listening on a body | The body keeps its conversation channel open and streams continuously; the core recognises "Hey Pebbo" as for the PC app. The cap is the mute button. | The firmware's own wake words are Chinese or English ("Hi ESP"); only the wake phrase "Hey Pebbo" is wanted. Continuous streaming also lets reminders be spoken at any time. | An on-device wake word, waking with a button |
| 57 | Case | Traced from the concept image at 1.3 times its size (about 175 mm tall), parametric in build123d with a collision check against the BOX-3, bracket and LED ring. The BOX-3 stays closed; a black visor funnel leads from the face to its screen and microphones; the speaker sounds through the torso grille. | The BOX-3 is taller than the concept's display. Keeping the proportions matters more than the exact size. Opening the BOX-3 would break its tuned acoustics. | Shrinking the head and losing the concept's look, opening the BOX-3 |
| 58 | Ahead of the gate | The body software, case and shopping list were made before all software phases were done, at the owner's request. Phase 3 to 5 still follow. | The owner wants to print and build Pebbo now | Waiting for the gate |
| 59 | Wake phrase on bodies | The name "Pebbo" also counts when speech recognition hears it as "people" or "Peppel", as happens with a body's compressed audio. | Measured with six synthetic voices through 16 kHz Opus: 31 of 36 wake phrases recognised and none of 30 other sentences. A lone "Hey Pebbo!" is missed most often; saying the request right after it works. A trained acoustic wake word stays the next step. | An on-device wake word of the firmware, which only offers Chinese and English phrases |
| 60 | Speed: deciding while answering | The action agent and the answer run at the same time (Ollama with `OLLAMA_NUM_PARALLEL=2`, which fits next to Whisper in 8 GB). A gate after the language model holds the answer until the decision is in and speaks the tools' confirmation right after the answer. Whisper transcripts are marked final, so the end of a turn does not wait for the speech recognition safety timeout. | Acting before answering added 0.5 to 1.5 s per sentence, and the turn end waited about 0.8 s for a transcript that was already there | Acting before answering, a separate decision model (does not fit in 8 GB) |
| 61 | Two instances | A second instance runs the same core with its own data directory, name and port. Instances pair with a six-digit code and exchange tokens. The peer API can only deliver a handoff; it cannot read anything. A handoff is prepared by a tool, approved or rejected by the owner in the control centre, logged on both sides, and arrives at home as a reminder for the person with the same name. Instance calls are accepted from private networks and private VPN ranges only. | Same features in both places with strict separation (decision 22). Approval keeps work data from reaching home unasked. | A shared database, automatic syncing |
| 62 | Model router | The owner lists compute devices (Ollama addresses with a model) in the control centre in order of preference. Pebbo checks them every 20 seconds and starts each conversation on the first reachable one, falling back to this computer. Without an NVIDIA GPU, speech recognition uses a small Whisper model on the CPU. Devices must be on the home network or a private VPN. | The always-on box must keep Pebbo working when the gaming PC is off (phase 6), and the owner manages compute devices in the settings (decision 5) | Fixed configuration files, switching mid-conversation |
| 63 | Smart home and music | Pebbo reaches Home Assistant, and Music Assistant through Home Assistant's media players, through Home Assistant's built-in MCP server. Any MCP server with Streamable HTTP is a tool source: the owner adds it in the control centre (name, URL, access token, permission), Pebbo lists its tools and registers each in the tool registry as `<server>_<tool>` with the server's description and JSON schema and the server's permission (household by default, everyone or owner only). The tool's short text answer, such as Home Assistant's "speech", is spoken after Pebbo's answer, otherwise "Erledigt." or "Das hat nicht geklappt.". | Capabilities stay tools picked by their descriptions (decision 50), so devices need no phrases or code. Home Assistant already maps names and areas to devices and limits Pebbo to the entities exposed to Assist. | A Home Assistant REST connector with own intents, controlling Music Assistant directly |
| 64 | MCP client | The official MCP Python SDK (MIT) with the Streamable HTTP client in the legacy handshake mode, a fresh session for every listing and call, a 6-second call timeout and proxies from the environment turned off. A failing server only changes its status in the control centre. Tokens and tool arguments are never logged at `INFO`, and failures are logged without tracebacks. | Maintained reference implementation, no telemetry (its OpenTelemetry API has no exporter). A session per call costs a few milliseconds on the home network and survives server restarts. Tracebacks could contain arguments or headers. | A hand-written JSON-RPC client, one long-lived session per server |
| 65 | Device states in the context | If a server offers Home Assistant's `GetLiveContext`, it is not an action. A compact summary of it (device, area, state, at most about 1200 characters) is added to the per-turn context of recognised household members, refreshed at most every 30 seconds and after each device action. An answer waits at most 1 second for a stale summary. Guests never get it, whatever the server's permission. `GetDateTime` is not offered, Pebbo knows the time. | The answer is written while the action agent decides (decision 60), so a query tool's result would arrive too late. With the states in the context Pebbo answers "Ist das Licht an?" truthfully. | Calling the state tool as an action, polling Home Assistant continuously |
| 66 | Addresses of MCP servers | An MCP server must resolve to a private, loopback or other non-public address. A public host is used only if the owner ticks "Öffentliche Adresse erlauben" for that server; then exactly that host is added to the runtime network guard and shown in the control centre, and removed again when the server is switched off, changed or removed. | Local first, and the owner sees every public host Pebbo may contact | Allowing any address the owner types, a global switch for public servers |
| 67 | Integration credentials | Access tokens are stored in the local database and are write-only in the control centre API: it reports only whether a token is stored. | A token should never travel back to a browser. Encryption at rest follows with the always-on box (see architecture). | Returning masked tokens |
| 68 | Teaching routines | Routines are taught through tools of the action agent: the action agent passes only the person's words to `teach_routine`, and a second, focused call to the model (`pebbo.routines.structure`) turns them into a trigger, conditions and actions in Pebbo's own JSON format, with the tools a routine may use and their arguments, and creates a draft, whose spoken result reads the routine back and asks. `confirm_routine`, `discard_routine`, `list_routines`, `pause_routine` and `test_routine` (dry run) follow the same way. A correction replaces the open draft. Nothing is active without the person's yes. | Same principle as decision 50: no phrases, the model picks tools by their descriptions, and the core checks and normalises what it sends. The read-back comes from the stored structure, so the person hears what will really run. The full routine format alone is about 1000 tokens; outside the action agent's tool list it leaves room in the 4096-token window for the tools of Home Assistant, and the focused call fills it in more reliably. | A separate routine dialogue with fixed questions, regular expressions for "wenn ... dann", saving without confirmation |
| 69 | Routine safety | A routine that watches another person, is marked as affecting others, doors, locks or alarms, or uses an owner-only tool needs the owner's approval: the owner's own yes, otherwise "Freigeben" in the control centre. Tool actions run with the approver's permissions, otherwise those of the person who taught it, checked by the registry on every run. Each routine has a cooldown (15 minutes) and a daily limit (6 runs), spoken output is suppressed in quiet hours (`PEBBO_QUIET_HOURS`, 22:00 to 07:00), and every run, skipped run and dry run is logged with trigger, conditions and actions. | Follows the safety rules in the features. Checking at run time, in the service that acts, stops a routine from gaining rights it was never given. | Checking permissions only while teaching, unlimited runs |
| 70 | Routine engine | The core runs routines itself with a scheduler next to the reminder scheduler, every 5 seconds, without a language model. Time and sunrise or sunset triggers fire once per scheduled moment and are skipped if missed by more than 10 minutes. Sunrise and sunset are computed locally from `PEBBO_LATITUDE` and `PEBBO_LONGITUDE`. Device triggers and conditions read a small `StateSource` protocol that integrations such as Home Assistant implement. Translating routines into Home Assistant automations is not done yet. | Routines keep working without the model and without Home Assistant, and every integration plugs in the same way | Running routines only as Home Assistant automations, a weather or location service for the sun |
| 71 | Presence (first step) | A person is "near Pebbo" and counts as home when speaker identification recognises their voice, and away after `PEBBO_PRESENCE_AWAY_MINUTES` (60) without hearing them. Arrivals and departures are events for routines. Presence is kept in memory only. Phone, app and Wi-Fi signals follow in phase 4. | The voice is the only local signal available today. Not storing presence avoids a movement history. | Waiting for phone presence before offering arrive and leave triggers, storing presence history |
| 72 | Local calendar first | Appointments live in tables of the instance database, per person or for the household, with read-only ICS subscriptions read by Pebbo's own small parser (`VEVENT`, `RRULE` basics, `EXDATE`). Radicale for phone subscriptions and the sign-in connectors (iCloud, Google, Microsoft 365) come later. | Briefings and the agent need appointments now. An own parser of about 250 lines avoids a dependency to audit, and unusual entries are skipped instead of breaking the calendar. | Starting with Radicale (separate GPL process, CalDAV client needed), the `icalendar` and `recurring-ical-events` libraries |
| 73 | Calendar hosts | A subscription contacts only the host in its address. Hosts on the home network are read directly. Any other host stays off until the owner allows it for that subscription; then that host alone is added to the runtime network guard and only HTTPS is used. Withdrawing or removing it revokes the host. No proxy is used, and the control centre shows only the host, never the full address. | Local first: an external host is contacted only when the owner enabled it and it is visible. Private calendar links contain a secret. | Allowing any subscription address, a fixed list of calendar providers, showing the full address |
| 74 | Morning briefing | The first time Pebbo recognises a person on a day from 05:00, and something is planned that day, the context asks the conversation model to offer an overview in its own words. The `daily_briefing` tool says the day's appointments, reminders and routines when the person wants it. Today's appointments are part of the recognised person's context, never a guest's. | Proactive but not pushy, without trigger words, and the overview comes from data instead of the model's memory | Speaking the briefing unasked, a fixed phrase such as "Briefing" |
| 75 | Cacheable prompts | The action agent's system prompt and tool list never change between turns; the time, the speaker, what Pebbo knows and the last lines go into the user message. The conversation model's system message starts with the unchanging persona, followed by the per-turn context. | Ollama reuses a cached prompt prefix. With the time at the start, nothing after it was reused and a decision over 15 tools took 1.1 seconds; with a stable prefix about 2000 of 2070 tokens come from the cache and a decision takes 0.2 to 0.4 seconds. | Fewer tools per request (a fixed preselection would be a trigger list), a larger context window (does not fit next to Whisper in 8 GB) |
| 76 | Phone pairing | The owner creates a pairing for one person in the control centre. It shows a six-digit code and a QR code with the core's address on the home network and the code. The code is valid for ten minutes and once; five wrong codes end every open pairing. The phone exchanges it at `POST /api/app/pair` for its own random token bound to that person. The core stores only SHA-256 hashes of codes and tokens and checks the token on every request, so removing a phone or its person ends access at once. | Same pattern as bodies and instances (single-use code, own revocable credential), and the person is chosen by the owner, not claimed by the phone. A copy of the database does not let anyone act as a phone. | Reusing the body pairing, where the device shows the code; a central Pebbo account; long-lived or reusable codes; storing tokens in plain text |
| 77 | App API on the home network (extends #55) | `/api/app/` is accepted from private addresses like `/xiaozhi/`, and from this computer for emulators. Requests with an Origin header and paths with `.` or `..` segments are refused there. The control centre, also its phone routes, stays on this computer only. Every app route except pairing needs the phone's token and acts only for its person. | Phones on the Wi-Fi must reach the core, the control centre still has no sign-in, and a web page in the owner's browser must not guess pairing codes | Opening the control centre to the network with a token; accepting public addresses before the relay exists |
| 78 | Text chat | The app's chat reuses the voice conversation's persona, per-person context message (with a line that the person writes in the app) and the action agent with the tool registry and its permissions. Deciding and answering run at the same time as in decision 60, and the answer passes the same honesty filter. Each phone keeps its last ten messages in memory only. Text chats are not summarised yet. | One personality and one way of acting for voice and text, no second prompt to maintain | A separate prompt for text; tools on the conversation model; storing chat transcripts |
| 79 | Pairing by QR code | The QR code holds a `pebbo://pair?address=…&code=…` link, drawn in the browser by uqr. The phone's own camera app opens the Pebbo app with it. The app has no in-app scanner. | expo-camera scans codes on Android with Google ML Kit, which may contact Google's servers and send usage metrics. The system camera needs no camera permission in the app. | expo-camera or react-native-vision-camera scanners; a QR image from a web service |
| 80 | Reminders on the phone before push | While the app is open it asks `GET /api/app/notifications` every 15 seconds for reminders that became due since its last acknowledgement, and acknowledges what it showed. An acknowledged reminder counts as delivered.
